## 3. THE NAME TRAP — read before editing any config

`enp4s0` still exists, and it still means "bus 4" — but **bus 4 is now the 10 GbE card, not
the CERN NIC.** The name survived the hardware change and silently changed meaning.

```
BEFORE 2026-07-22:   enp4s0 = I210      = CERN net (128.141.177.0/24, DHCP)
AFTER  2026-07-22:   enp4s0 = AQC113    = DREAM net (192.168.10.0/24, static, MTU 9000)
                     eno1   = I219-LM   = CERN net       (was DREAM)
```

**Both interfaces swapped roles while `enp4s0` kept its name.** Identify NICs by driver or
MAC, never by name, when reasoning about anything written before today:

```bash
for i in /sys/class/net/*/; do n=$(basename $i); [ "$n" = lo ] && continue; \
  printf '%-10s %-9s %s\n' "$n" \
  "$(basename $(readlink -f $i/device/driver 2>/dev/null))" "$(cat $i/address)"; done
# atlantic -> DREAM/FEU   |   e1000e -> CERN
```

### Consequence for `system_stats` analysis — THIS WILL BITE

`NET_IFACES = ["enp4s0", "eno1"]` in **both** `flask_app/app.py:1312` and
`system_monitor/system_stats_controller.py:59` is still *literally correct as strings* — so
nothing errors, nothing looks broken, and the CSV keeps logging. **But the columns now mean
the opposite of what they meant yesterday.**

- `net_eno1_rx_bps` — was **DREAM/FEU readout**, is now **CERN**.
- `net_enp4s0_rx_bps` — was **CERN**, is now **DREAM/FEU readout**.

The entire 1 GbE saturation measurement (see `04_bandwidth_model.md` and
`scripts/analyze_link_load.py`) integrates `net_eno1_rx_bps`. **Pre-upgrade ladders must be
analysed with `--iface eno1`; post-upgrade ladders with `--iface enp4s0`.** Mixing them
silently compares CERN idle traffic against FEU readout and yields nonsense.

**Rotate the day's CSV** at the swap boundary so the two regimes are never in one file:

```bash
mv ~/beam_july/slow_control/system_stats/system_stats_2026-07-22.csv{,.pre_10g}
```

`_log_row()` writes a header only when the file does not exist, so appending across the
change puts new-meaning rows under old-meaning column names with no error and no warning.

## 5. CERN / LanDB MAC registration — the thing that actually blocked us

**The plan documents did not mention this at all, and it was the only real blocker.** Neither
the card nor the driver nor the slot caused a single problem. This did.

### The mechanism

CERN's LanDB registers each device by **MAC address**. Move the CERN cable to a different NIC
in the same machine and the DHCP server does not recognise you. You are not refused outright —
you are handed an address in the **unregistered holding range `172.20.179.0/24`**, which looks
like a working DHCP lease and is not the network you want.

Evidence from this machine's own lease history (`/var/lib/NetworkManager/internal-*.lease`,
root-only directory, mode 700):

| Date | NIC in `enp4s0` | Lease | Reading |
|---|---|---|---|
| 2026-01-30 | I210, newly plugged | `172.20.179.99` | unregistered → holding range |
| 2026-03-06 | I210, after registration | **`128.141.177.103`** | registered → real subnet |
| 2026-07-22 15:44 | AQC113, new MAC | `172.20.179.93` | unregistered → holding range again |
| 2026-07-22 15:55 | I219-LM (`eno1`), real MAC | **no lease at all** | not even the holding range |

### The workaround (used 16:00–17:23, now REMOVED)

`eno1` presented the removed I210's MAC (`b4:96:91:4d:1a:95`) via netplan `macaddress:`.
CERN saw a registered MAC and issued the same `128.141.177.103` as before. **Removed at
17:23** once the real MAC was registered — kept here because it is the right first move any
time a CERN cable moves to a different NIC.

**This is safe *only* because the I210 is physically out of the machine** — there is no
duplicate MAC on the wire. The scripts that set this up refuse to run if they find an I210
(`8086:1533`) on the PCI bus or that MAC live on any interface.

**It is a bridge, not a destination.** Until it is removed, this box reports a MAC belonging
to hardware it does not contain, which will mislead the next person to debug it.

### The proper fix — LanDB procedure (performed 2026-07-22 16:07, completed 17:23)

The device already exists; **do not use "Register Device"** — that creates a duplicate
competing for the same name and IP.

1. Go to `landb.cern.ch`, search **`NTOF-X17-DAQ`** (or the IP, or the MAC).
   Reverse DNS confirms the device: it resolves to `ntof-x17-daq.dyndns.cern.ch`.
2. Device page → **DHCP Information → Network Interface Cards** → **Edit**.
3. **Add** the new MAC in LanDB's dash/uppercase format: `8C-EC-4B-B4-AC-64`.
   **Add rather than replace** — with both MACs registered there is no window in which
   neither works, because the clone keeps carrying the lease until the new one propagates.
   A pending address shows an hourglass icon; both rows show a "Last seen" timestamp, which
   is *switch* observation and **not** proof of propagation.
4. Wait for the hourglass beside the new address to clear (~15–30 min; it took ~45 here).
5. Remove the clone on the machine — **use the self-healing script**, which also restores
   `mtu: 1500`:
   ```bash
   sudo bash -c 'setsid nohup bash docs/network_upgrade_10g/scripts/cern_unclone_safe.sh \
        > /home/mx17/cern_unclone.log 2>&1 < /dev/null &'
   tail -f /home/mx17/cern_unclone.log
   ```
   It applies, waits up to 120 s for an address in `128.141.177.0/24` **with a pingable
   gateway**, and **auto-restores the clone if that fails** — so a premature run costs only
   a retry. Outcome is written to `/home/mx17/cern_unclone_result.txt`.
   *(`cern_drop_mac_clone.sh` is the earlier, simpler version: no auto-rollback, no MTU fix,
   not detached. Prefer `cern_unclone_safe.sh`.)*
6. **Delete the `B4-96-91-4D-1A-95` row in LanDB** once the real MAC holds the lease. A
   registered MAC for a card that no longer exists is exactly the sort of stale entry that
   outlives everyone who understands it. **Done 2026-07-22 — CERN cutover complete.**

**Result:** succeeded first try at 17:23:53, ~8 s from apply to a verified lease.
`eno1` → `128.141.177.17` on the real MAC, MTU 1500, gateway + DNS OK, DREAM untouched.
Old row deleted afterwards with no effect on connectivity, as expected.

### Before deleting a MAC row — how to be certain which one is real

Getting this backwards costs you CERN access, and the two MACs here are visually
confusable: the keeper `8C-EC-4B-B4-AC-64` *contains* `B4-AC-64`, while the one to delete
*starts* with `B4-96`. Do not go by eye. Four checks, run on the machine:

```bash
ethtool -P eno1                       # PERMANENT (burned-in) address — the decisive test
ip -br link | grep -i <suspect-mac>   # is the suspect MAC on any interface at all?
ip -4 -br addr show eno1              # which iface holds the live CERN lease
lspci -nn | grep -i 8086:1533         # is the old card even still on the bus?
```

`ethtool -P` is the one that settles it: it reports the address burned into the silicon,
**not** the one netplan `macaddress:` set. While the clone was active, `ethtool -P eno1`
already read `8c:ec:4b:b4:ac:64` while `ip link` showed `b4:96:91:4d:1a:95` — the exact
signature of a spoof. Delete the MAC that is **not** any interface's permanent address.

Verified before deletion: permanent == current == `8c:ec:4b:b4:ac:64`; `b4:96:…` absent from
every interface; the live lease bound to `eno1`; no I210 on the PCI bus.

> **`sudo` + `setsid` ordering matters.** `sudo setsid nohup … &` **hangs**: `setsid`
> detaches from the controlling terminal before `sudo` can prompt, and with stdin on
> `/dev/null` it has nowhere to ask — the process sits in state `T` forever and the script
> never starts (0-byte log). Put `sudo` on the *outside*: `sudo bash -c 'setsid nohup … &'`,
> so it prompts on your real terminal and the already-root shell does the detaching.
> `sudo -v` first does **not** fix the original ordering — sudo's credential cache is
> per-tty (`tty_tickets`) and `setsid` gives the child a different tty.

Note: **IP addresses = "No IP addresses found"** on the device page — there is no static
reservation. The address comes from the dynamic pool and is sticky **by MAC**, so it
**changed `.103` → `.17`** when the clone came off. Nothing in this repo depends on it
(everything references the DAQ host as `192.168.10.8`), and DNS follows both forward and
reverse — **refer to this host by name**. The LanDB Wi-Fi credential `ntof-x17-daq@cern.ch`
is tied to this device record — never delete and recreate the device.

## 6. Gotchas discovered during the cutover

Four things that cost time and are not in any of the plan docs.

**Netplan does not reset an MTU it was not told about.** `eno1` came out of the DREAM config
at MTU 9000. The first CERN profile omitted `mtu:`, expecting the hardware default — the
interface silently stayed at **9000 on a 1500-byte CERN segment**. DHCP still worked (small
packets), so nothing looked wrong. **Always state `mtu:` explicitly when repurposing an
interface.**

**`netplan apply` resets `nmcli dev set <if> managed no`.** Parking an unconfigured interface
that way does not survive the apply, and NetworkManager promptly invented a junk auto-profile
(`Wired connection 3`) that started DHCPing the DREAM network. Delete junk profiles *after*
the apply, or give the interface a real profile instead of parking it.

**NetworkManager penalises default routes by +20000 when its connectivity check fails.**
`eno1`'s default route appeared at metric **20090** instead of the requested 90, so a USB
tether at metric 100 kept winning. CERN's network blocks the Ubuntu connectivity-check URL,
which is why the check fails. It resolved itself when the tether was unplugged. If a tether or
second uplink is ever present again and CERN inexplicably loses the default route, this is
why — fix it with `connectivity.enabled=false` in NetworkManager, not by fighting metrics.

**`netplan apply` prints alarming `systemd-networkd` errors under the NM renderer.**
`"Failed to reload network settings: Unit dbus-org.freedesktop.network1.service not found.
Falling back to a hard restart of systemd-networkd.service"` — cosmetic on this box, which
uses the NetworkManager renderer. Not an error.

### ⚠ Test 3 (jumbo) cannot be performed with `ping` on this segment

The first attempt reported `*** JUMBO FAILED ***` against `192.168.10.240`. **That is a
test artefact, not a switch fault.** A size ladder isolates it:

| target | largest DF frame echoed | what it means |
|---|---|---|
| N1081B `.240` | **1500** | the CAEN board's own stack is MTU 1500 |
| FEU `.83` | **2023** (binary-searched; 2027 fails) | the FEU's ICMP echo buffer, ~2 kB |
| FEU `.43` | same | identical, so it is the FEU design not one board |

Two conclusions:

1. **The switch is not a 1500-only switch** — a 2023-byte frame traverses host → switch →
   FEU → switch → host. Anything blaming the switch for the 9000 failure is wrong.
2. **No endpoint on 192.168.10.0/24 can echo a 9000-byte frame**, so `ping -M do -s 8972`
   can never pass here regardless of the switch. `01_tx401_install.md` and
   `02_feu_switch_migration.md` both prescribe this test; **it is not a valid test on this
   segment** and will produce a false failure every time.

The jumbo path that actually matters is **one-directional, FEU → host**, carrying readout
frames up to the FEU cap of 8192 (`MultiPackThr` 4888). It is exercised only during a run.
For the *current* switch it is already proven by operation: `eno1` ran MTU 9000 through this
same switch for days with clean readout at IPD ≥ 75 and 311 kB/event.

**When the area switch is replaced, verify jumbo like this instead:**

```bash
# during a short run, on the DAQ host
sudo tcpdump -i enp4s0 -n -c 200 'src net 192.168.10.0/24 and udp' -e | \
  awk '{print $NF}' | sort -n | tail -5      # expect frame lengths well above 1500
```

A new switch silently defaulting to MTU 1500 would show every readout frame clamped near
1500 — and would look like corruption, not like a config error. That is the failure mode
`00_system_readiness` §5 warns about, and this is how to catch it.
